ResearchGenie: Gap Implementation Plan

This plan maps every open lab gap to a buildable change that makes the product better for its users. It is grounded in the code as of 18 Oct 2026. Size: S = under ~150 lines, M = 150–500, L = over 500 or a new subsystem.

Principle. No feature exists only for marks. Each workstream fixes a real product pain: a 15-minute run lost to one failure, vague questions that waste a run, thin corpora, claims nobody can audit, and an install that evaluators can't do. Each workstream reuses code already in the repo (llm_provider, discovery/sources, _http_retry, ollama_manager, LangGraph, the contracts) and adds at most one new dependency (mcp).

WS1 — Run Ledger & Resume

S–ML6 · L10 · L12
Pain today: events live only in run_registry._runs (a dict), so a server restart loses every run's history. If Verification fails at minute 14, nothing can be re-run except the whole pipeline. run_pipeline has no resume path.

Build

  1. Event ledger. In orchestrator/pipeline.py, add a 10-line wrapper around run_pipeline that appends each yielded event to <run_dir>/events.jsonl before passing it on. Every consumer (CLI, API, web) gets it for free.
  2. Registry from disk. In run_registry.get_run(), when the id is not in memory, rebuild a finished RunState from outputs/*_<run_id>/events.jsonl and metadata.json. The SSE replay already handles a list of past events.
  3. Resume from a stage. Add run_pipeline(..., resume_dir: Path | None, from_stage: int | None). For each stage before from_stage, load 0N_*/result.json with the stage's contract (DiscoveryResult.model_validate, etc.) and skip the service call. Default from_stage = the first stage with no result.json.
  4. Versioned finals. When a resume would overwrite final/, move the old one to final_v1/ first and record "resumed_from_stage" in metadata.json. This is the rollback: nothing is lost, and both versions can be compared.
  5. Surfaces. researchgenie resume <run_dir|run_id>, POST /research/runs/{id}/resume, and a "Resume" button on failed runs in frontend/index.html.

Done when

  • A test fakes a failure in Verification, then resumes. Discovery and Writing are not called again (mock call counts = 0), and final/ plus final_v1/ both exist.
  • After a server restart, GET /research/runs/{old_id} still returns status and events.

Risk: low. Contracts already round-trip through JSON (they are tested), so reloading saved results is safe.

WS2 — Doctor: self-healing runs

ML10
Pain today: the common failures each have a known fix in the code (ollama_manager.start_ollama_server, pull_model), but the user only sees an error string. This is the "diagnose and fix a failed deployment" task from the reference worklet, applied to the team's own product.

Build

  1. researchgenie/doctor.py: deterministic diagnosis, the same approach as QA (no LLM grading the system). It reads the last failed event in events.jsonl (from WS1), checks /system-style readiness, and matches the failure against a rule table:
    Signal (already emitted today)DiagnosisAutomatic fix
    LLMProviderError "Could not reach the local Ollama server"Ollama is not runningstart_ollama_server(), then resume (WS1)
    "Model '…' is not installed"The model is missingpull_model() with progress, then resume
    "No papers found in any source" + source_error ×NAll sources rate-limited or offlineWait for the Retry-After window, then resume from Discovery
    "No paper … judged relevant"The question is too narrow or vagueHand over to the clarify step (WS4), propose keywords
    draft_status: partial / broken_sectionsThe model failed a section auditResume from Writing (the graph's SQLite checkpoint keeps finished work)
    No paper.pdfNo LaTeX toolchainReport only: print the tectonic install hint
  2. Output: diagnosis, evidence (the event lines), the proposed fix, and a prompt to confirm before applying it. Auto-apply only with --yes. Write a doctor_report.json into the run folder (audit trail).
  3. Surfaces: researchgenie doctor [run], POST /research/runs/{id}/doctor, and a "Diagnose & fix" button next to the WS1 "Resume" button.

Done when

  • Live demo: stop Ollama mid-run → the run fails → doctor identifies "Ollama not running", restarts it, resumes, and the run completes.
  • One unit test per rule row, using the recorded event lines as fixtures.

Depends on WS1. Keep the rule table data-driven (a list of tuples), so a new failure adds one row and no new code path.

WS3 — Ship it: container, CI, cloud demo

ML10 · L11 · L14
Pain today: trying the product means installing Ollama and pulling 6.6 GB. There is no CI, so the 319 tests run only when someone remembers. Gemini has never produced a draft.

Build

  1. Dockerfile: python:3.11-slim, pip install -r requirements/base.txt && pip install ., and tectonic for PDFs. CMD uvicorn orchestrator.api:app --host 0.0.0.0.
  2. docker-compose.yml with two profiles. local: app + ollama/ollama (GPU passthrough, model volume, OLLAMA_HOST pointed at it). cloud: app only, with AI_PROVIDER=gemini.
  3. Cloud demo on one CPU VM (no GPU cost) running the cloud profile. This is also the place to verify Gemini for the first time (gap B-19). Put the key in an env var, never in the image.
  4. .github/workflows/test.yml: run pytest on push and PR. The live tests already skip when Ollama is unreachable, and the full-pipeline test is gated by AI_RESEARCH_RUN_FULL_PIPELINE, so CI stays fast with no changes.

Done when

  • A green CI badge, with the recorded test count replacing the unproven "320".
  • A public URL where /system shows model_ready: true and one full Gemini-backed run completes. Its run folder goes into docs/.

Risk: the free Gemini tier may hit rate limits on a 15-minute run. If so, the demo uses the Short length preset. A GPU VM is the fallback, at a cost.

WS4 — Adaptive Discovery

ML1 · L2 · L13
Pain today: the steps are fixed. Discovery always searches PubMed, even for civil engineering. A vague question runs the full 15 minutes before it fails. A thin corpus (fewer accepted papers than corpus_size) is analyzed as is, never searched again.

Build (three small, separable pieces)

  1. Clarify (L1). Add analysis.clarify_question(), one complete_json call with think=False and the schema {specific: bool, missing: [str], suggested_question: str}. CLI: if not specific, show the suggestion and accept, edit or keep it. Web: an inline prompt before the run starts. Skip for unattended runs.
  2. Model-chosen tools (L2, L13). Add llm_provider.chat_tools(system, user, tools), which sends Ollama /api/chat with "tools": [...] and returns message.tool_calls. Expose the four sources as tool schemas (search_openalex(query), …), each mapped to the existing sources/*.search. The model picks the tools and the query for each tool. Deterministic fallback: if there are no or invalid tool calls, or on Gemini, use DEFAULT_SOURCES filtered by domain, so MECHANICAL/CIVIL/EEE drop PubMed. Emit a tool_plan event so the choice is visible in the log and the UI.
  3. Observe → revise loop (L1). In discovery/pipeline.py, after screen_papers(): if len(accepted) < corpus_size and round < 2, call generate_queries again. The prompt gets the rejected titles and reasons (already in the relevance_filter event) and the instruction "avoid these, target the gap". Search again, merge, dedupe, screen. Emit {"type":"replan","round":2,"reason":…}.

Done when

  • A civil-engineering question logs a tool_plan without PubMed. A biomedical question includes it.
  • A deliberately narrow question shows replan round 2 and ends with more accepted papers than round 1.
  • Tests: a fake model returns no tool calls → the fallback path is used. The replan stops at 2 rounds.

Risk: whether qwen3.5:9b calls tools reliably is unproven. Run a 30-minute spike first. The deterministic fallback means the product never gets worse.

WS5 — Research Library (cross-run memory)

ML4
Pain today: full-text retrieval (Europe PMC → OA PDF) is the slowest and flakiest network step, and it repeats from scratch every run. Past runs are never read again. Design constraint found in the code: literature cards can't be reused across runs, because their cache key includes the tag definitions, which are specific to each question (literature_card.py:99). So memory works at the paper level, not the card level.

Build

  1. shared/utilities/library.py: stdlib sqlite3 at ~/.researchgenie/library.sqlite, next to the existing config. Tables: 
    papers(doi PK, title, abstract, year, venue, discussion_excerpt, fulltext_status, first_seen)
runs(run_id PK, question, created, overall_quality, draft_status, run_dir)
run_papers(run_id, doi, selected BOOL)
papers_fts / runs_fts  -- FTS5 over title+abstract / question
  2. Write: one call at the end of run_pipeline (next to metadata.json), plus a one-time researchgenie library import that backfills from the existing outputs/ and docs/research-papers/ runs.
  3. Read 1, full-text cache: in _collect_fulltext, look up the DOI first. On a hit, reuse discussion_excerpt and skip the network. Emit {"type":"memory_hit","papers":n}.
  4. Read 2, related work: before Discovery, run an FTS search of runs_fts for the new question and emit related_runs. The UI shows "You researched a similar question on 13 Sep (QA 4.2) → open".
  5. Read 3, candidate seeding: previously selected papers whose FTS score matches the question join the candidate pool before the relevance gate, so they still have to pass it. This adds recall without bypassing the safety check.

Done when

  • A second run on a related question logs memory_hit with a count above 0, and its Discovery time drops measurably (record both timings).
  • Tests: an FTS lookup round trip; the gate still rejects a seeded paper that is off topic.

Plain FTS5 needs no new dependency. Embeddings stay out until FTS recall measurably falls short. This is still RAG, with lexical retrieval; say so honestly.

WS6 — Scholarly connector + MCP server

ML5
Pain today: services/verification/service.py::_resolves() has no retry, so one rate-limited Crossref call marks a real reference "unverifiable". It also has its own HTTP client, separate from the shared one. Nothing speaks MCP.

Build

  1. One connector. Move Verification's DOI lookups onto the shared discovery/sources/_http_retry.py GET, and its OpenAlex lookup onto sources/openalex.py (add work_by_doi()). Product effect: fewer false "unverifiable" results. Measure it by re-verifying the 11 saved runs before and after.
  2. MCP server, researchgenie/mcp_server.py, on the official mcp SDK (FastMCP, stdio) with entry point researchgenie-mcp. It has the three tool families from the reference worklet:
    FamilyToolsBacked by (existing code)
    Filelist_runs(), read_run_artifact(run_id, name)outputs/. Only names that are already allowed (the API's FINAL_FILES), with a path-traversal guard.
    SQLitesearch_library(query), run_summary(run_id)WS5 library.sqlite (read-only connection)
    APIsearch_literature(query, sources), verify_doi(doi)discovery/sources/*, the Verification check_reference

Done when

  • MCP Inspector or Claude Desktop lists the 6 tools, and verify_doi classifies a real DOI and a made-up one correctly.
  • The before/after "unverifiable" count across the 11 saved runs is recorded.

Adds the one new dependency (mcp), justified because MCP is a protocol. Read-only by design: the MCP server can't start runs or write files.

WS7 — Auditable output: evidence table, paper approval, governance

S–ML9 · L12
Pain today: the evidence trail exists (literature_cards/*.json, the verification results), but no user ever sees it. Writing starts on whatever papers Discovery chose, with no chance to drop a weak one.

Build

  1. Evidence table (deterministic, no LLM). Add shared/utilities/evidence_table.py, which joins the literature-card points (by tag), the section ↔ tag map from the writing artifacts, and the verification status by DOI. The orchestrator writes final/evidence_table.md (paper · point · section used · DOI · verified/invalid/unverifiable). Add it to FINAL_FILES so the web UI and API can download it, and add an "Evidence" tab in the results view.
  2. Paper approval gate. Add an optional approve: Callable[[DiscoveryResult], Awaitable[DiscoveryResult]] parameter on run_pipeline, called after Stage 1. CLI: a table of the selected papers (relevance score, year, venue) where the user can drop some by number, backfilled from the ranked candidates. Web/API: the run status becomes awaiting_approval, and POST /research/runs/{id}/approve resolves an asyncio.Event on the RunState. Default = auto-approve, so tests, the smoke scripts and unattended runs don't change. Record the approval in events.jsonl (WS1): who, which papers were dropped, and when.
  3. Governance doc, docs/governance.md: risk → control → where it is in the code → how to roll back. Example rows: invented citation → Verification, 3-way; off-topic paper → relevance gate + approval gate; unsupported claim → section audit omits it; key leak → header auth (D-023); bad output → WS1 versioned finals + resume.

Done when

  • Every new run has final/evidence_table.md, and each row's DOI matches a references.md entry (a test asserts this).
  • In the web UI the run pauses after Discovery, a paper is dropped, and the draft does not cite it.

WS8 — Dev Agent (agentic SDLC factory)

LL11
Make it useful to the product: not a toy code generator, but an agent that implements small, well-specified tickets in this repo under test control. A human approves the diff. Its demo ticket is a real product feature: add APA citation style (today only IEEE/Springer exist, in citation_formatter.py).

Build

  1. devagent/graph.py: a LangGraph StateGraph, reusing the Lab 7 pattern: 
    read_ticket → plan (files to touch, acceptance criteria)
  → write_failing_test → run_pytest (expect RED)
  → write_patch → run_pytest
  → [green?] → END : [round < 3] → write_patch (with the pytest failure output fed back)
  → present_diff (human approves; never commits or pushes)
  2. Tools: read_file, apply_patch (limited to the paths in the plan), and run_pytest(test_path) through subprocess with a timeout. It works in a git worktree, so the main tree is never touched. The model is reached through llm_provider, like every other service.
  3. Audit: each round's prompt, patch and pytest output go to devagent_runs/<id>/, the same ledger style as WS1.
  4. Entry point: researchgenie-dev "<ticket text or path to a spec .md>".

Done when

  • A saved run on the APA ticket shows RED → GREEN with no hand edits, and the approved diff is merged as a normal commit. APA then becomes an option in the CLI and the web UI.

Risk: a 9B local model is weak at multi-file edits. Keep tickets to a single module with an obvious test. Use Gemini for this agent if the local model fails, and report which one produced the result. The human approval gate is required.

Deliberately left out

  • Vector embeddings: add only if FTS5 recall measurably misses related runs.
  • Kubernetes or multi-node deploy: one container on one VM is enough for a demo and a course.
  • An LLM-based doctor: rules cover every failure the code emits today, and the doctor stays deterministic like QA. An LLM explanation can be added later if unknown failures appear.
  • Auto-commit in the Dev Agent: a human approves every diff, always.
