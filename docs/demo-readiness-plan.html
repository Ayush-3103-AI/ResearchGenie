ResearchGenie: Demo Readiness Plan

How we take every lab week from "built" to "shown working", and get the product ready for the final review with the professor and other stakeholders. Grounded in the repo as of 23 Oct 2026: main has R1 and R2 (PRs #29, #30), and r3/integration has R3 (not merged). It follows on from gap-implementation-plan.html (18 Oct) and updates lab-worklet-weekly-draft.html (23 Oct).

Assumption about dates. We do not have the review date in the repo. This plan uses Day 1 = Sat 24 Oct and makes the product demo-ready on Day 12 (Wed 4 Nov), with two spare days before a review in the week of 9 Nov. If the review is earlier, cut Phase 4 (PyPI) first, then the hosted URL. Never cut the live checks in Phase 1. They turn "tested on a fake model" into "shown working".

2. What "demo-ready" means (exit criteria)

We say we are ready only when every box below has evidence in the repo. A statement in a sheet with no evidence does not count.

  1. All code on main. R3, R4 and R5 are merged through PRs, CI is green, and the full pytest count is recorded.
  2. Every week of the sheet says "Implemented". Each row links to a file, a test and a real-run artifact. The 18 Oct "Partial", "Process only" and "No rollback" labels are gone.
  3. Real-model evidence is committed: the spike numbers (#16), the Doctor recovery (#13), the Dev Agent APA run (#26), advisor gap statements (#27), 3 fresh full runs (#27) and one Gemini run (#24).
  4. Three ways to see it work: (a) live on the GPU laptop, (b) a hosted URL on Gemini, (c) a recorded video, used only if (a) and (b) both fail on the day.
  5. Stakeholder pack: the final lab sheet with a novelty line for each week, a 12-minute demo runbook, golden run folders and a short deck.

4. Phases

Phase 1 — Close R3 with the three live checks

Days 1–3GPU laptopWeeks 2 · 10 · 11 · 5 · 12
Why first: R3 is built and tested but blocked from main by three checks that need a real model (r3-live-checks.md). Every later phase stacks on R3, and three weeks of the sheet move to "Implemented" when it lands.

Do

  1. Spike (#16): python scripts/spike_tool_calling.py --json spike.json. Paste the summary (e.g. 9/12 valid, 8/12 sensible) on #16 and commit spike.json under docs/evidence/. Keep the model step on only if it is at least 8/12 valid. The domain fallback covers the other cases.
  2. Doctor demo (#13): start a --length short run, stop Ollama during Writing, run researchgenie doctor <run_id>, and confirm. Record the screen. Commit doctor_report.json (its outcome must read "Fix applied; the resumed run completed.") and a GIF. Do it once in the web UI too (Diagnose & fix → Apply fix).
  3. Dev Agent APA (#26): researchgenie-dev --spec docs/tickets/26-apa-7.md. Check that the audit shows red, then green. Apply patch.diff with no hand edits, run the full suite and commit it. Fill in the Result line in the ticket. If qwen fails in 3 rounds, rerun on Gemini and say so in the ticket.
  4. Container, local profile (#23): docker compose --profile local up, pull the model, and check that /system reports model_ready. Then close #23.
  5. Open the PR r3/integration → main, merge it once CI is green, and close #6, #10, #13, #16, #20, #22, #26.

Done when

  • R3 is on main. docs/evidence/ has the spike JSON, the Doctor report and recording, and the Dev Agent audit summary. Weeks 2, 5, 11 and 12 are "Implemented" with links to that evidence.

Risk: qwen 9B tool calling may score low. That is fine: report the measured number honestly and show the fallback working. An honest number earns more marks than a claim with no number.

Phase 2 — R4: budget check, library reads, decision brief

Days 1–6Dev laptop (in parallel with Phase 1)Weeks 4 · 9 · 10 · 12
Why now: none of R4 needs a model. Every check in it is deterministic, so it can be built on the dev laptop while the GPU laptop does Phase 1. Branch r4/integration off r3/integration now, not off main, and rebase it once R3 merges.

Build, in this order

  1. #7 Budget check. The gateway estimates OpenAlex credits from the planned searches (search = 10, filter = 1, entity = 0) and emits budget_check before Discovery. If the balance is short, it offers "add key" or "reduced plan" (headless runs take the reduced plan and say so). DOI lookups use OR-filters of up to 100 DOIs. Test: N DOIs make ceil(N/100) requests. Week 10: the agent prevents a failure, it does not only recover from one.
  2. #19 Discovery reads the library. Reuse stored Discussion excerpts by DOI, and emit memory_hit. Seed matching past papers into the candidate pool before the relevance gate, so memory can never get past the safety screen (test: an off-topic seeded paper is rejected). --no-memory restores today's behaviour. Week 4: retrieval is now used by a later run.
  3. #12 Decision brief. final/decision_brief.md is built from QA, verification counts, draft status, broken sections, gateway events and memory hits by a rule table, with no LLM call (asserted). It has exactly one recommended next action. Show it on the CLI completion screen, in result --json, and as a new panel in the web results view. Keep the Ayudh theme tokens and the current layout. Add the panel only.

Done when

  • Each acceptance box on #7, #19 and #12 is ticked by a test. The PR r4/integration → main is merged after R3.
  • On the GPU laptop (Day 8): two related runs back to back, with the second run's Discovery time and memory_hit count recorded in analytics_and_results.md.

Phase 3 — R5: one skill for Claude Code and OpenClaw

Days 6–9Dev laptop + account holderWeeks 3 · 6
Why: this is the only thing between Week 6 and "Implemented", and it makes Week 3 a real skill that two runtimes share. It depends on the headless CLI (#10), the Doctor (#13) and the decision brief (#12), so it comes after Phase 2.

Build

  1. skills/researchgenie/SKILL.md follows the Agent Skills spec: name, description, and OpenClaw requires gating (binary researchgenie, optional OPENALEX_API_KEY / contact email). Use relative paths only.
  2. Instructions call only fixed command lines that can be allowlisted: researchgenie status --json, run … --json (detached, timeout ≥ 30 min), result, resume, doctor. No inline code and no pipe-to-shell.
  3. When a run finishes, the reply holds the decision brief plus paths to draft.md, paper.pdf and the evidence table.

Done when

  • The skill passes the reference validator and loads in Claude Code and in OpenClaw. A recorded demo shows a question sent from Telegram/WhatsApp, a background run, and a finish message. "How is my run going?" returns the status.
  • Install and publish steps are documented. The act of publishing is left to a human.

Fallback if OpenClaw cannot be set up in time: demo the same skill in Claude Code, and say on the sheet that OpenClaw loading is verified but the chat-app recording is pending. Do not claim the recording.

5. Novelty: what we claim, and the evidence for each claim

Each line says what ResearchGenie does that a plain LLM writer or chatbot does not. Every claim must point to a test or a real run. If the evidence is not in the repo by Day 12, the claim leaves the sheet.

WeekNovelty claimEvidence
1The agent asks a clarifying question only when the question is vague, and re-plans the search only when the corpus is too thin. Both triggers are deterministic, not the model's mood.test_clarify.py, test_discovery_replan.py, live demo
2The model picks the databases, but each tool call is checked against the domain (for example, no PubMed for mechanical engineering), with a fallback. All calls go through one gateway that knows each host's credits and pacing.spike.json (#16), test_scholarly_gateway.py
3One skill folder runs in two agent runtimes because the skill only calls a fixed, allowlistable headless CLI.skills/researchgenie/, validator output, recording
4Memory makes later runs faster but cannot get past safety: seeded past papers still go through the relevance gate.test (off-topic seed rejected), measured second-run time
5A read-only MCP server exposes runs, the library and a DOI checker that classifies a reference and never repairs it, with path-traversal refusals.test_mcp_server.py, MCP Inspector demo
6A durable per-run event ledger lets a run be watched from a terminal, a browser or a chat app, and it survives a server restart.events.jsonl, test_api.py, chat recording
7Two cooperating graphs: a 9-node checkpointed writing graph, and a Dev Agent graph that improves the product itself.writing/graph.py, dev_agent/
8The gap-mining swarm keeps a gap only when several independent papers raise it (a recurrence threshold). A barrier test proves the workers really run in parallel.test_trend_gap_mining.py, real advisor run
9Every claim in the draft traces to a row of an evidence table: paper → evidence point → section → DOI → verification status. Future-work claims are checked against a fresh search.evidence_table in each golden run
10A self-healing ops agent: a rule-table diagnosis with quoted evidence, a human confirmation, then a resume from the failed stage. A budget check stops a run before it can fail on credits.doctor_report.json, recording, test_doctor.py
11The Dev Agent shipped a real product feature (APA 7): the test fails first, the fixes are search/replace edits, existing tests run as guards, and it works in a throwaway worktree. It never commits; a human applies the diff.audit folder, merged APA commit
12Rollback through versioned finals (final_v1/, final_v2/). QA is deterministic and independent of the model that wrote the draft. Each run ends with exactly one recommended next action.test_resume.py, GOVERNANCE.md, decision_brief.md
13Topic ranking for each engineering field comes from real OpenAlex publication counts, not the model's opinion. The search adapts its sources to the field.advisor runs in 6 fields, real gap flags
14The whole system runs on a local 9B model on an 8 GB laptop GPU, with no cloud cost or data leaving the machine, and switches to Gemini with one setting.golden runs, hosted URL
