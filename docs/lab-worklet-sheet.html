Lab 1 — Agent vs Chatbot

Implemented
Agent loop & the plan–act–observe–revise cycle (vs a stateless chatbot)
1. Concept appliedResearch Discovery takes one research question and runs a multi-step loop to a result. A chatbot would answer one prompt. Plan: the model writes the search queries. Act: the agent calls the scholarly APIs. Observe: it dedupes, applies a relevance gate, and handles source failures. Revise: it re-ranks the papers. The clearest revise step is in Research Writing: every drafted section is audited, and a section that fails gets one revision round.
2. Technical stackPython 3.11, asyncio. Local Ollama qwen3.5:9b through shared/utilities/llm_provider.py (JSON-schema-constrained output). httpx. LangGraph for the writing loop.
3. Implementationdiscovery/pipeline.py::run_pipeline() runs these stages: generate_queries (LLM), search across 4 sources, dedupe and rank, relevance gate (relevance.py), full-text mining, mine_future_research, checking each candidate against a fresh search, and analyze_gaps (LLM). Each stage emits a real progress event (status, source_error, relevance_filter, corpus, …).
Revise loop: writing/graph.py audits each section (section_auditor.audit_section) and revises it, with max_section_revision_rounds=1 in services/research-writing/service.py. When a literature card fails validation, the retry prompt gets the validation errors (D-019).
4. Evidenceservices/research-discovery/discovery/pipeline.py, discovery/analysis.py. Live run on "effects of intermittent fasting on cognitive performance": 120 papers found → 118 unique → 6 selected, with 11 gaps and 5 future-research candidates (docs/reviews/review_1.md).

Correction: the old text said the agent "decides its own multi-step plan". It does not: the order of steps is fixed in code. The model decides the queries and the gap analysis. Calling "re-rank" the revise step is weak; the writing audit → revise loop is the real one.

Lab 2 — Tool-Using Agent

Implemented
Tool integration & function calling
1. Concept appliedDiscovery acts through four real external tools: the Semantic Scholar, OpenAlex, PubMed and arXiv search APIs, plus open-access full-text retrieval. The local LLM is also called as a tool, for query generation and gap analysis, and it returns structured JSON.
2. Technical stackhttpx.AsyncClient; asyncio.gather for concurrent calls; one adapter per tool; a shared bounded exponential-backoff GET that honors Retry-After; Ollama format = JSON schema.
3. Implementationdiscovery/sources/semantic_scholar.py, openalex.py, pubmed.py and arxiv.py each wrap one API. All four share _http_retry.py (D-028). The search stage calls all four in parallel. When a source fails, the agent emits a source_error event and continues with the rest. Every result is normalized into one Paper model.
4. Evidenceservices/research-discovery/discovery/sources/*.py; tests/services/test_discovery_http_retry.py. Rate-limit failures that degraded gracefully are recorded in review_1.md and D-028.

Correction: the agent does not use a native function-calling API, where the model picks the tool. Code calls the tools, and the model only returns schema-constrained JSON (the queries for each source). Say this plainly if asked.

Lab 4 — Memory & Retrieval

Partial
Short-term state vs long-term retrieval (RAG)
1. Concept appliedShort-term memory is the LangGraph ReviewState, which lives for one writing run. Persistent memory is a SQLite checkpoint per run, so an interrupted writing graph can resume. Every stage's output is also saved to disk. Retrieval works over the evidence of the current run: tag-based recall of literature-card points when a section is written.
2. Technical stacklanggraph-checkpoint-sqlite (AsyncSqliteSaver); JSON files; deterministic tag-tree recall (hierarchical_recall.py); open-access full-text retrieval in Discovery (Europe PMC JATS, then OA PDF).
3. Implementationwriting/graph.py runs the graph with a checkpoint at <run>/checkpoints.sqlite ("run or resume"). orchestrator/pipeline.py writes 00_request.json, 01_discovery/ … 04_quality_assurance/result.json, final/ and metadata.json under outputs/<slug>_<run_id>/. hierarchical_recall.py provides direct, rollup, leaf and subtree recall of evidence points by tag for each section.
4. Evidenceorchestrator/pipeline.py, writing/graph.py, writing/modules/hierarchical_recall.py. Saved runs: docs/research-papers/<topic>/<run_id>/ (11 runs) and docs/sample-output/.

Not implemented: no vector store and no embeddings (relevance.py says this). No run reads earlier runs back. Saved runs are an audit trail, not long-term memory that a later run retrieves. Retrieval is deterministic tag recall, not semantic RAG.

Lab 6 — OpenCLA / OpenClaw Runtime

Implemented (custom runtime)
Agent runtime with logging
1. Concept appliedOne orchestrator runtime runs all the agents for one request: optional Stage 0, then Discovery → Writing → Verification → QA. It logs every stage's output for audit and streams standard progress events to the terminal, an HTTP API, or the browser.
2. Technical stackPython async generators; FastAPI + uvicorn; SSE; an in-memory run registry; JSON audit trail; Rich terminal UI.
3. Implementationorchestrator/pipeline.py::run_pipeline() loads each service by file path (_load_service()), runs the stages in order, and saves each stage's result.json. It converts each service's own event format into one standard event: {run_id, stage, service, status, title, message, details, timestamp}. orchestrator/api.py offers POST /research (sync), POST /research/runs + GET /research/runs/{id} + /events (SSE), /advisor/runs…, /health and /system. run_registry.py tracks background runs.
4. Evidenceorchestrator/pipeline.py, orchestrator/api.py, orchestrator/run_registry.py, tests/orchestrator/. Terminal screenshots for each stage: docs/phase-3/images/03–08*.svg.

Note: this is the team's own runtime. It does not use OpenCLA/OpenClaw.

Lab 7 — Agentic Node Graph

Implemented
Graph-based orchestration (LangGraph)
1. Concept appliedResearch Writing is a LangGraph state graph. Explicit nodes and edges decide how a draft is built. Conditional edges route on the graph's own state: fan-out per paper, then which section to write next, then when to stop.
2. Technical stackLangGraph (StateGraph, START/END, Send); langgraph-checkpoint-sqlite.
3. Implementationwriting/graph.py::build_review_graph() has 9 nodes: initialize → define_tag_semantics → discover_documents → [build_literature_card ×N] → build_tag_index → analyze_tag_coverage → plan_writing_order → write_section (loop) → write_review → END. Three conditional edges: dispatch_cards, route_to_section, continue_sections. The graph is compiled with a SQLite checkpointer. A second graph, trend_advisor/gap_mining.py, runs the advisor's swarm.
4. Evidenceservices/research-writing/writing/graph.py lines 913–933; tests/services/test_writing_*.py.

Lab 8 — Parallel Swarm

Implemented
Parallel execution, swarms & fault-tolerant merge
1. Concept appliedWorker agents run in parallel, and their results merge into one shared output. When one worker fails, it is audited, retried, or skipped. The whole run does not crash.
2. Technical stackLangGraph Send() for dynamic fan-out; asyncio.gather(..., return_exceptions=True).
3. ImplementationWriting: dispatch_cards() sends one build_literature_card worker per selected paper. Each card is validated, and a failed card is retried with its errors. All cards then merge into build_tag_index. Discovery runs three parallel stages: the 4-source search, full-text fetch, and candidate checks. A failed source emits source_error and the run continues. Trend Advisor: gap_mining.py sends one mine_paper worker per candidate paper. The merge keeps only gaps that several independent papers raise (a recurrence threshold, D-033).
4. Evidencewriting/graph.py (dispatch_cards), discovery/pipeline.py, trend_advisor/gap_mining.py, tests/services/test_trend_gap_mining.py (an asyncio.Barrier test that fails if the workers run in sequence, D-038). The writing fan-out ran in every real pipeline run (11 saved in docs/research-papers/).

Caveat: the gap-mining swarm is tested only against a fake model. Two later advisor runs (ECE and Cloud/DevOps, 28–29 Sep) logged no "model unavailable" warning, but neither flagged any gaps. No run has shown useful gap statements from a real model yet.

Lab 9 — Deep Research Agent

Implemented
Deep research with evidence synthesis
1. Concept appliedDiscovery does multi-hop research. It searches several databases, filters for relevance, reads the full text of papers (Discussion, Limitations, Future work), extracts what the authors say is still open, and checks each such claim against a fresh search. Writing then turns that evidence into a cited draft. Every claim must come from a paper in the corpus.
2. Technical stackSemantic Scholar, OpenAlex, PubMed and arXiv (all keyless). Europe PMC JATS / open-access PDF (pypdf, defusedxml). Local LLM with JSON schemas. LangGraph for the writing synthesis. IEEE / Springer citation formatting.
3. ImplementationResearch path: generate_queries → 4-source search → dedupe → relevance gate → full-text mining (fulltext.py) → mine_future_research → check against a fresh search → analyze_gaps. The output is gaps with evidence and impact, plus a novelty assessment with a confidence level.
Evidence synthesis: each paper becomes a literature card of tagged evidence points (LiteratureCard, saved as literature_cards/P00x.json). The cards are indexed by tag, and each section is written only from its tag's points. Citations go into a numbered reference list. Since D-039, the full-text Discussion excerpt also goes to Writing (evidence_depth: abstract_plus_discussion).
4. Evidencediscovery/analysis.py, discovery/fulltext.py, writing/schemas.py::LiteratureCard. 11 real runs, each with draft.md, references.md, validation_report.md, quality_report.md and paper.pdf, on 3 topics: intermittent fasting, remote work, urban green space (docs/research-papers/).

Gaps: the final output has no human-readable "evidence table"; the per-paper evidence lives in the literature-card JSON. D-039 (Discussion text sent to Writing) passes its tests, but its effect on paper length has not been measured in a live run.

Lab 10 — Cloud Operations Agent

Partial (observability + failure handling only)
Cloud agents, observability & failure handling
1. Concept appliedObservability and failure handling are built into the runtime. Every stage reports status live, model readiness is checked before a run starts, external APIs are retried with backoff, and failures are reported to the user. The system does not return a confident empty result.
2. Technical stackFastAPI health and status endpoints; SSE event stream; _http_retry.py (bounded exponential backoff, Retry-After); researchgenie/ollama_manager.py; optional Gemini (cloud) provider.
3. ImplementationObserve: GET /health, and GET /system (provider, model, model_ready, shown in the UI header before a run). GET /research/runs/{id} returns status and error, and /events streams over SSE. metadata.json records warnings, errors and draft_status.
Handle: all 4 sources retry on transient errors (D-028). A failed source degrades gracefully. PipelineError becomes HTTP 502. ollama_manager detects Ollama, starts it, installs it, and pulls the model. A timeout is reported as a timeout, not as a failed install (D-042). The Gemini key moved to a header after a key leak in an error message (D-023).
4. Evidenceorchestrator/api.py, discovery/sources/_http_retry.py, researchgenie/ollama_manager.py, tests/researchgenie/test_ollama_manager.py, tests/orchestrator/test_api.py, DECISIONS D-023 / D-028 / D-042.

Not implemented: no cloud deployment, no Dockerfile or CI pipeline in the repo, and no agent that diagnoses and fixes a failed deployment. Docker was used only to test install paths (D-024). A successful winget install was never observed, and no full draft has been generated through Gemini.

Lab 12 — Safety & Governance

Implemented (no rollback)
Approval gates, audit logs, evaluation, rollback
1. Concept appliedA human approves before the agent acts. Every stage leaves an audit record. The output is evaluated by an independent, deterministic checker, not by the model that wrote it. Unsupported content is removed or flagged; it is never silently "repaired".
2. Technical stackRich Confirm prompts; JSON audit artifacts; a deterministic QA service (no LLM); Crossref/OpenAlex DOI checks; completeness.py.
3. ImplementationApproval gates: "Start research?" (researchgenie/cli.py:203). "Lock in topic?", default No (advisor_cli.py:263). "Run the full pipeline now?" (advisor_cli.py:338). The orchestrator never picks a topic by itself (D-034).
Audit: per-stage result.json, card_audits/*.json, and metadata.json.
Evaluation: Verification classifies each reference as verified, invalid or unverifiable, and never repairs one. QA scores 0–5 on four dimensions plus an overall score, with no LLM calls. draft_status (complete, partial or failed) is computed from the rendered paper.
Containment: a section that fails its audit is replaced with a notice, and the failed draft is kept in the audit artifact (graph.py:139–144). API keys are stored only in the local config.
4. Evidenceservices/quality-assurance/service.py, services/verification/service.py, services/research-writing/completeness.py, tests/services/test_qa_service.py, tests/services/test_verification_service.py, tests/services/test_completeness.py. Example reports: docs/sample-output/final/quality_report.md, validation_report.md.

Not implemented: no rollback. The SQLite checkpoint lets the writing graph resume, not undo. Each run writes a new folder, so earlier runs are never overwritten, but nothing reverts a run.

Lab 13 — Discipline-Specific Agents

Partial (data half verified, model half not)
Domain worklet for the team's discipline
1. Concept appliedThe Trend & Gap Advisor (optional Stage 0) is specialized for each engineering discipline. A student picks a domain, and the advisor ranks the rising research topics in that field. The ranking uses real publication counts, not the model's opinion. The core worklet itself is a CSE (AI) research-assistant agent.
2. Technical stackOpenAlex field and topic APIs, with counts by year; arXiv as a second source for CS-adjacent domains; LangGraph Send gap-mining swarm; separate entry point researchgenie-advise.
3. Implementationadvisor_cli.DOMAINS: CS/AI/ML, ECE, EEE, Mechanical, Civil, Cloud/DevOps, and Other (free text). trend_advisor/velocity.py computes growth as papers in the last 3 complete years ÷ papers in the 3 years before, using OpenAlex field IDs checked against the live API. gap_mining.py mines the stated future work of each topic's papers. parse_pick resolves "go with #2" in code, not with the model. A confirmed pick fills a ResearchRequest and can chain into the 4-stage pipeline under one run id (D-040).
4. Evidenceservices/trend-advisor/, researchgenie/advisor_cli.py, tests/services/test_trend_*.py. 8 saved advisor runs in 6 domains: outputs/{cs-ai-ml ×3, ece, eee, civil, mechanical, cloud-devops}_*/00_trend_advisor/result.json. Each has 6–8 ranked topics with real growth numbers and example DOIs.

Gap: every saved run has 0 gap flags. Earlier runs logged "local model was unavailable", which means gaps were not checked, not that none exist. Gap statements, the converging chat, question drafting and the live hand-off to the pipeline have not been shown working with a real model (TILL_NOW.md, "Next technical task").

Lab 14 — Capstone Project Studio

Implemented
End-to-end, team-owned agentic system
1. Concept appliedResearchGenie is one installable system that uses the course concepts together. It has an agent loop, tools, skills with contracts, persistent state, a runtime with an audit trail, a node graph, a parallel swarm, deep research, approval gates and independent evaluation. Users reach it through a terminal app, an HTTP API, or a browser workbench.
