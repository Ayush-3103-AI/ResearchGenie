ResearchGenie: Technology Report

Agentic AI (26ECAC401) · KLE Technological University, Belagavi · CSE (AI) · Team 7. This report covers the code on main at e52276d (27 Oct 2026, after PR #31) and the live pass on the GPU laptop on 26 Oct (docs/evidence/live-pass/LIVE_PASS.md). Every number in it is measured, including the failures.

ResearchGenie turns a research question into an evidence-grounded paper draft with verified citations. A team of agents runs on a local 9B model (qwen3.5:9b, RTX 4060 8 GB): they find and screen the literature, mine the full text for open problems, write a cited draft, check every reference against scholarly databases, and score the result with a deterministic checker. Around that pipeline sit a Trend Advisor that suggests topics, a Doctor that repairs failed runs, and a Dev Agent that changes the product's own code under test. A human approves the corpus and confirms every fix.

2. How a run works

  1. Start. The student types a question in the terminal, web or chat, or picks a rising topic from the Trend Advisor. If the question is vague, the agent asks one clarifying question. A budget check estimates the OpenAlex credits the run will use. If the balance is short, the student can add a free key or run a reduced plan that uses Crossref.
  2. Discovery. The model plans which databases to search with native tool calling, and code checks each choice against the field (no PubMed for mechanical engineering). Four sources are searched in parallel through the gateway. Past papers from the library are seeded in, the results are de-duplicated and ranked, and a relevance gate screens everything. If too few papers remain, it re-plans with new queries once. Full text (Discussion, Limitations, Future work) is mined, and each "open problem" is checked against a fresh search before gaps are analysed.
  3. Approval. The student sees the screened papers and approves the corpus before any writing starts.
  4. Writing. A 9-node LangGraph turns each paper into a validated literature card of tagged evidence points, using a parallel Send() fan-out. It indexes the cards by tag, plans the section order, and writes each section only from its tag's evidence. Every section is audited; a section that fails is revised once, or replaced with a notice.
  5. Verification. Every reference's DOI is checked in batches against Crossref, then OpenAlex. Each one is classified verified, invalid or unverifiable. Nothing is repaired.
  6. QA. A deterministic checker with no LLM scores citation integrity, claim–source alignment, process control and literature coverage (0–5), plus an overall score.
  7. Output. final/ holds the draft, the LaTeX and PDF, the references, the validation and quality reports, an evidence table (paper → point → section → DOI → status) and a decision brief with exactly one recommended next action. The run and its papers go into the library.
  8. If it fails. Every event is already in events.jsonl. The Doctor matches the failure against a 12-rule table: Ollama stopped, model missing, credits exhausted, all sources failed, no relevant paper, partial draft, missing LaTeX, and so on. It quotes the evidence and proposes the fix. After the student confirms, it applies the fix and resumes from the failed stage, keeping the earlier output as final_v1/.

3. Week by week

Week 1 · Agent vs Chatbot

ImplementedLive: shown
Concept
An agent loop (plan → act → observe → revise) instead of one prompt and one answer.
Stack
Python asyncio, Ollama qwen3.5:9b with JSON-schema output, LangGraph.
Implementation
discovery/pipeline.py: model-written queries → search → observe (dedupe, relevance gate, source errors) → revise (re-plan when the corpus is thin, #15). A clarify step handles vague questions (#14). In writing/graph.py, each section goes through audit → revise.
Evidence
test_clarify.py, test_discovery_replan.py; 4 fresh live runs.
Novelty
The agent adapts only when the evidence says so, through deterministic triggers. Its behaviour can be explained and tested.

Week 2 · Tool-Using Agent

ImplementedLive: shown
Concept
Function calling: the model chooses the tools.
Stack
Ollama/Gemini native tool calling, httpx, a scholarly gateway (per-host token buckets, Retry-After, circuit breaker).
Implementation
The model returns a tool plan (database + query). Code validates it, with a fallback by field (#16). All HTTP goes through scholarly_gateway.py (#3). The budget check estimates credits and batches DOI lookups at 100 per request (#7).
Evidence
Live spike: 12/12 valid tool plans, 11/12 sensible on the 9B model. A test shows 250 DOIs take 3 Crossref requests + 1 OpenAlex request.
Novelty
The model chooses, but code checks each choice against the field. The gateway knows each provider's credits, so a run stops before it fails.

Implemented

Week 4 · Memory & Retrieval

ImplementedLive: shown
Concept
Short-term state vs long-term retrieval.
Stack
LangGraph state + SQLite checkpoints; SQLite FTS5 library; SQLite response cache.
Implementation
The library stores every run and paper (#18). The cache keeps searches 7 days, DOIs 30 days and full text indefinitely (#6). Discovery reuses stored excerpts by DOI and seeds matching past papers before the relevance gate (#19). --no-memory turns this off.
Evidence
On the live related run, memory_hit found 10 papers (1 excerpt reused, 9 seeded). Its Discovery time was 259.8 s against 239.5 s for the first run: seeding adds papers to screen, so it made the corpus larger, not faster. A test shows an off-topic seed is rejected.
Novelty
Memory can never get past the safety screen: past papers are judged again for every new question.

Implementation

Week 10 · Cloud Ops Agent

ImplementedDoctor fixed 27 Oct, live re-run pending (#13)
Concept
Observability, failure handling, an agent that diagnoses and fixes.
Stack
GitHub Actions CI, Docker (local / cloud profiles), FastAPI /health + /system, a rule-table Doctor.
Implementation
CI on every push (#2); a container with an Ollama and a Gemini profile (#23); the Doctor (#13), with 12 rules → fix → confirm → resume, also in the web UI as Diagnose & fix; the budget check (#7); a hosted-demo recipe (#24).
Evidence
test_doctor.py has one test per rule (12 rules). In the 26 Oct live pass, Ollama was killed during Writing, but the run completed instead of failing. That is by design: Writing isolates each card and section, so a dead model leaves a broken draft, not an error. The live-pass script only called the Doctor on failed runs, and the Doctor would have proposed rewriting the draft while Ollama was still down. Fixed on 27 Oct: a new rule, ollama_stopped_mid_writing, starts Ollama and then rewrites from Writing. The web UI now offers Diagnose & fix for a finished run with a broken draft, and the live-pass step diagnoses either outcome. The live re-run is pending.
Novelty
A self-healing ops agent with no guessing: it quotes its evidence, a human confirms, and the run resumes instead of restarting.

Implementation
